SHEINAR PAYMENT FLOW WORKTREE
==============================

This document shows the implemented payment flow, conditional branches, and
expected behavior for success, failure, cancellation, retries, concurrency,
webhooks, duplicate payments, refunds, and security cases.

3. MULTIPLE TRAFFIC / MULTIPLE INITIATION CASES
================================================

CASE A: User double-clicks Pay
------------------------------
Condition:
  Two create-order requests arrive almost together.

Expected:
  - Same cart fingerprint is generated.
  - MongoDB PaymentAttemptLock allows only one winner.
  - Winner receives HTTP 201 with one Razorpay order.
  - Loser receives HTTP 409.
  - No second active Razorpay order is created.

CASE B: Two browser tabs start payment
--------------------------------------
Condition:
  Tab A and Tab B use different idempotency keys for the same cart.

Expected:
  - Cart fingerprint is the same.
  - One request receives 201.
  - Other request receives 409.
  - Tab B checks payment status instead of opening another charge.

CASE C: Same idempotency key is replayed
----------------------------------------
Condition:
  Network retry sends the same Idempotency-Key again.

Expected:
  - Backend returns 409 for the already-used key when the original opaque
    access token is unavailable.
  - No new local order.
  - No new Razorpay order.

CASE D: First request fails at Razorpay
---------------------------------------
Condition:
  Local attempt exists but gateway order creation fails.

Expected:
  - Attempt marked failed.
  - Active lock released.
  - A later retry can create a fresh attempt.
  - No order is marked paid.

CASE E: One tab pays, another tab cancels
-----------------------------------------
Condition:
  Tab A captures payment. Tab B submits an old cancellation.

Expected:
  - Tab B can change only its own attempt if it is still cancellable.
  - Captured attempt remains captured.
  - Local order remains paid.
  - Fulfilment executes once.

CASE F: Two genuine captured payments
-------------------------------------
Condition:
  Two different Razorpay payment IDs become captured for one local order.

Expected:
  - First capture atomically marks the order paid.
  - Second payment is marked duplicate.
  - Second payment is not silently ignored.
  - Admin reconciliation/refund is required.
  - Fulfilment and confirmation email run once.


4. STALE SESSION AND RECOVERY CASES
===================================

CASE A: Browser closes after payment
------------------------------------
1. Payment may have been captured.
2. Browser does not receive callback.
3. Session token remains in sessionStorage.
4. On refresh, frontend calls GET /api/payments/status/:attemptId.
5. If paid, show confirmation and clear session.
6. If pending, show checking message and do not charge again.
7. If failed/cancelled, allow a new attempt.

CASE B: Old INR tab and new USD tab
-----------------------------------
- Each attempt stores immutable currency and amount.
- INR attempt cannot verify USD payment.
- USD attempt cannot verify INR payment.
- Currency changes never mutate existing Razorpay orders.

CASE C: Old failure arrives after success
-----------------------------------------
- Failed webhook or stale browser callback cannot downgrade paid order.
- PaymentAttempt and Order states remain terminal/paid.

CASE D: Payment ID reused across orders
---------------------------------------
- Server finds existing PaymentAttempt with that payment ID.
- New attempt becomes duplicate.
- Verification returns conflict.
- No cross-order fulfilment.

6. PAYMENT SUCCESS AND RETURN CASES
===================================

SUCCESS:
  Razorpay captured + server verification succeeds
  -> PaymentAttempt = captured
  -> Order.paymentStatus = paid
  -> Order.status = paid
  -> successfulPaymentAttemptId saved
  -> fulfilmentProcessed set once
  -> one confirmation notification scheduled
  -> frontend shows Order Confirmed

PENDING:
  Gateway status is authorized or uncertain
  -> attempt remains non-final/pending or authorized
  -> order does not fulfil
  -> frontend shows Checking payment status
  -> customer is not immediately charged again

FAILED:
  Gateway reports failed or verification fails
  -> attempt = failed
  -> order remains unpaid
  -> active lock released
  -> customer can retry with a new attempt

CANCELLED:
  Customer closes Checkout before capture
  -> attempt = cancelled
  -> order remains unpaid
  -> customer can retry

DUPLICATE:
  A second payment is captured for an already-paid order
  -> attempt = duplicate
  -> order remains paid
  -> no second fulfilment
  -> refund/manual reconciliation required

REFUNDED:
  Authorized admin refund succeeds
  -> PaymentRefund = processed
  -> Order.refundedAmount updated
  -> refundStatus = partially_refunded or refunded
  -> original payment history remains intact


7. TEST COMMANDS
================

Backend:
  cd backend
  npm test

Frontend unit tests:
  cd my-app
  npm test

Frontend production build:
  cd my-app
  npm run build

Playwright E2E, after installing Chromium:
  cd my-app
  npx playwright install chromium
  npm run test:e2e

E2E must use mocked payment endpoints or Razorpay Test Mode. Never use real
customer card numbers, CVV, OTPs, or live payment credentials in automation.
